## Выполненные исправления

- `build:web` теперь обязательно проверяет готовый `dist` и возвращает ненулевой exit code при ошибке. Существующая генерация уникального 20-значного hex ID на каждый production-запуск сохранена; версия берётся из `package.json`.
- Новый `verify:web` проверяет SHA-256 всех ресурсов, согласованность HTML/JSON/worker, Web App Manifest и конфигурацию Pages. Проверка читает итоговые файлы и **не перегенерирует** метаданные поверх повреждённых байтов.
- HTTP-режим проверяет реальные MIME, `no-store` worker/метаданных, прямые маршруты и HTTP 404 отсутствующих файлов. Полный worker сравнивается с шаблоном **текущего checkout**, включая исполняемый код.
- Добавлены `public/404.html` и точные rewrite-правила существующих вкладок, включая завершающий `/`. Неизвестные URL не должны превращаться в успешную оболочку SPA. Локальный сервер воспроизводит эти правила.
- Убраны принудительные MIME `/sw.js` и `/version.json`, маскировавшие fallback. Существующие файлы получают MIME по расширению; политики кеширования сохранены.
- `404.html` исключён из precache: Pages канонизирует HTML URL, а worker намеренно отклоняет redirect при установке.
- Исправлено завершение первой подготовки: `current` подтверждается готовым кешем, совпадением worker/документа/проверенных метаданных и отсутствием другого устанавливаемого/ожидающего кандидата.
- В существующую карточку версии добавлено «Обновление успешно установлено.» при совпадении ID реально загруженного HTML с целью безопасного reload. При недоступном sessionStorage ложного подтверждения нет.
- Добавлены регрессионные проверки хранения, миграций, файлового SQLite и настоящего анкетирования с двумя полными перезапусками браузера и офлайн-правками. Зависимости не добавлялись; дизайн Apple Minimal сохранён.

## Архитектура локального хранения

Архитектура сохранена: UI → `ProfileProvider` / настройки → репозитории → `SettingsStorage` (`get`, `list`, атомарный `apply`). Веб использует IndexedDB `masstracker`, native — SQLite `masstracker.db`. SQLite Web/WASM для пользовательских данных не применяется.

`user_state` хранит версию формата, профиль и цель, активность, тренировочные и пищевые параметры, статус/черновик/шаг анкеты. Имя, пол, дата рождения, рост, текущий и целевой вес восстанавливаются; возраст вычисляется из даты рождения. Тема и базовые настройки хранятся отдельно. Демонстрационные записи остаются в памяти и не подменяют личный профиль.

Черновик сохраняется при вводе; редакторы разделов подтверждают сохранение после commit по существующей кнопке. Последовательная очередь исключает перезапись последнего ввода более ранней операцией. До восстановления состояния не создаётся новый профиль. Ошибка чтения/формата не затирает базу; отказ записи сохраняет форму и возможность повторить действие. Ограниченный веб-режим при недоступном хранилище явно сообщает о проблеме.

IndexedDB остаётся v2, SQLite — миграции 1–2. Новых миграций не потребовалось. Проверено, что ошибка upgrade откатывает версию и оставляет старые записи. Будущие сущности добавляются отдельными репозиториями и аддитивными миграциями; функционал следующих этапов не реализован.

## Механизм офлайн-режима

Регистрация `/sw.js`, scope `/`, `updateViaCache: none` не блокирует чтение профиля. Из готового экспорта кешируются HTML, все отложенные JS-вкладки, CSS, изображения и иконки. Иконки интерфейса встроены в JS как SVG, шрифт системный; внешний CDN не требуется.

Worker проверяет SHA-256, отклоняет redirect, ограничивает параллелизм и время загрузки. Готовность подтверждается полным кешем и совпадением версии документа/worker. «Подготовить офлайн-режим» повторяет регистрацию/восстановление и проверку результата. Пропавший ресурс отменяет готовность. Все пять вкладок используют согласованную оболочку; при утрате HTML показывается понятный fallback.

Кеш `masstracker-app-<buildId>` содержит ресурсы приложения. IndexedDB/SQLite отделены от него. Подготовка, отказ обновления и очистка старых ресурсных кешей не удаляют профиль, тему и завершённую анкету.

## Механизм обновлений

Проверки выполняются при запуске, возврате на страницу/из фона, восстановлении сети, по видимому почасовому интервалу и кнопке. `version.json` обходится без HTTP-кеша. Новая сборка полностью скачивается до предложения установки; «Обновить» применяет её, «Позже» откладывает уведомление.

Текущая оболочка не получает HTML другой версии до безопасного перехода. Стабильные URL ресурсов привязаны к ID документа. Старый рабочий кеш сохраняется при отказе кандидата и до подтверждённого запуска новой версии; кеш параллельно устанавливаемой следующей сборки не удаляется.

Формы и диалог темы блокируют активацию. Перед reload ожидается commit очереди, повторяются проверки форм и других окон. Ошибка разрешает повторное сохранение. После controllerchange выполняется один явный reload; sessionStorage предотвращает повторный reload той же цели. Подтверждение установки основано на реально загруженном ID. Остальные состояния — проверка, актуальная версия, загрузка, готовность, отсутствие сети и ошибка — остаются текстовыми и доступными для вспомогательных технологий.

## Настройки Cloudflare Pages

Доступа к панели нет: текущие production branch и Build command непосредственно в ней **не подтверждены**. Требуемая конфигурация:

1. Cloudflare Dashboard → **Workers & Pages → проект fitapp → Settings**.
2. В **Builds / Builds & deployments** установить production branch `main`.
3. В **Build configurations**: preset `None`, Build command `npm run build:web`, Build output directory `dist`. Root directory — корень репозитория с `package.json`; Windows-путь `D:\FitApp` туда не вводить.
4. Использовать совместимый Node.js, например `NODE_VERSION=24.22.3`, и устанавливать devDependencies, необходимые сборке.
5. Публиковать весь результат одного `build:web` одним deployment. Отдельного `expo export`, папки `public` или старого worker поверх нового `dist` недостаточно.
6. Проверить наличие `_headers`, `_redirects`, `404.html`. Не добавлять catch-all `/* /index.html 200`; вкладки перечислены явно. Не преобразовывать байты экспортированных ресурсов. Если есть дополнительные Cache Rules, проверить их на конфликт с `no-store` worker/метаданных.
7. **После разрешения публикации** выполнить deployment, затем `npm run verify:web -- https://fitapp-epj.pages.dev`. Это проверит ответы production origin; установленная PWA требует отдельной приёмки.

Заголовки: HTML/обычная статика — `no-cache, no-transform`; worker/метаданные — `no-store, no-cache, must-revalidate, no-transform`; хешированные JS/CSS — годовой immutable. Реальные локальные HTTP-ответы проверены тестами. Применение удалённым CDN после новой публикации ещё не проверено.

Первоисточники: [сборка Pages](https://developers.cloudflare.com/pages/configuration/build-configuration/), [SPA fallback и 404](https://developers.cloudflare.com/pages/configuration/serving-pages/), [rewrite-правила](https://developers.cloudflare.com/pages/configuration/redirects/).

## Ограничения и статус приёмки

- Физический iPhone, standalone PWA iOS и Expo Go недоступны; реальная приостановка/возобновление iOS и обновление установленной PWA требуют ручной приёмки.
- Production остаётся в выявленном несогласованном состоянии до разрешённых push/deployment.
- Без доступа к устройству нельзя подтвердить причину ранее потерянного профиля или восстановить отсутствующие записи.
- Обновление кода не очищает данные. Ручная очистка, удаление приложения и вытеснение браузером/ОС не дают гарантии сохранности; persistent storage запрашивается при доступности. См. [WebKit Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/).
- Verifier сравнивает worker с текущим checkout; исторической публикации соответствует её checkout. Backend, облачная авторизация и новые зависимости не требуются.
- Этапы не переводятся в `COMPLETED` только по автоматическим проверкам. Следующий этап не начинается.
