# HOTFIX 01.1 — Complete PWA Offline Mode

Дата проверки: 26.11.2026. Работа выполнена в `D:\FitApp`, только в рамках 01.1. Production и GitHub не изменялись. Этап остаётся `IN_PROGRESS` до согласованной публикации и ручной приёмки на физическом iPhone. План 02–15 и исходный канонический план не изменены.

## Диагностика и установленные причины

Проверен опубликованный [MassTracker](https://fitapp-epj.pages.dev), а не только исходники. Service Worker **уже существовал**; отсутствие SW не было причиной. На момент проверки production использовал версию `0d9050edcee46277b988`.

| HTTP-проверка                     | Фактический результат                                                                          |
| --------------------------------- | ---------------------------------------------------------------------------------------------- |
| `/` и `/profile`                  | 200, `text/html; charset=utf-8`, одинаковая SPA-оболочка                                       |
| `/sw.js`                          | 200, `application/javascript; charset=utf-8`                                                   |
| `/manifest.webmanifest`           | 200, `application/manifest+json; charset=utf-8`                                                |
| HTML, SW, manifest                | `Cache-Control: no-cache, no-transform`                                                        |
| Все 34 URL из production precache | 200; 34/34 SHA-256 совпали; типы JS, CSS, PNG и manifest корректны                             |
| Регистрация                       | `/sw.js`, scope `/`, `updateViaCache: none`, HTTPS                                             |
| Manifest                          | `id`, `start_url`, `scope` — `/`; `display: standalone`; локальные PNG                         |
| Критические ресурсы               | Локальные; пути зависимостей `/assets/vendor/`, без исключаемых Pages каталогов `node_modules` |
| Шрифты и интерфейсные SVG         | Системный шрифт; SVG встроены в JS. CDN-запросов при запуске не обнаружено                     |
| IndexedDB                         | Локальная база `masstracker`, версия 1, `app_settings`; открытие и чтение не обращаются к сети |

В чистых профилях Edge и Playwright WebKit **исходная опубликованная версия после полного precache прошла офлайн reload и закрытие/повторное открытие страницы**. Поэтому утверждение «production вообще не содержит офлайн-кеша» было бы неверным.

В коде и воспроизводимых браузерных тестах установлены конкретные дефекты:

1. `ready` вычислялся как `Boolean(navigator.serviceWorker.controller)`. После удаления необходимого ресурса из Cache Storage приложение продолжало сообщать «Доступно без интернета». Контроллер не гарантирует сохранность всего кеша. Это воспроизведено удалением CSS, с последующей офлайн-перезагрузкой.
2. После ошибки **первой регистрации** обработчик `online` вызывал только `registration?.update()`. Переменная регистрации оставалась пустой, повторного `register()` не было. Это воспроизведено ответом 503 на первый `/sw.js`, затем восстановлением сети: приложение оставалось без офлайн-подготовки.
3. После **неуспешной первой установки** из-за ресурса регистрация может не иметь ни active, ни installing, ни waiting worker. Для неё `update()` не восстанавливает установку. Требуется повторный `register()`. Проверено ответом HTML вместо CSS с HTTP 200 и последующим восстановлением правильного ресурса.
4. Прежний генератор вызывался внутри Metro serializer до записи окончательного HTML: HTML загружался и проверялся отдельно в install, но не имел собственной контрольной суммы. Для проверяемой целостности всей оболочки генерация перенесена после Expo export.

Это доказанные дефекты механизма готовности и восстановления. **Нельзя доказать, какой из них сработал на конкретном iPhone**, без состояния его Service Worker/Cache Storage. Пользователь сообщил iOS **27.2.1**. Физическое устройство недоступно; воспроизведение исходного сбоя на нём остаётся открытым. Возможное различие окружений Safari и standalone нельзя объявлять установленной причиной без проверки на устройстве.

## Механизм исправления

`npm run build:web` запускает Expo Web export, затем сканирует готовый `dist`. Генератор формирует `sw.js` и `precache-manifest.json`. Текущая сборка содержит **35 ресурсов**: итоговый HTML по `/`, десять JS-модулей, CSS, manifest и локальные изображения. Шрифты/SVG при появлении отдельных файлов также включаются автоматически; существующие SVG находятся в JS, шрифт системный.

Служебные `_headers`, metadata, sourcemaps и сам SW исключены из precache. Каталог `_expo` и его файлы с подчёркиваниями включаются полностью. Пути с `@` сохраняются. Проверяются ссылки HTML, CSS `url()` и иконок manifest; недостающие или внешние критические ресурсы отклоняют сборку. Скрипт Node.js использует стандартные файловые API и `process.execPath`, без PowerShell/bash-команд. Проверен на Windows; отдельный запуск в Linux не выполнялся.

Версия `masstracker-app-<20 hex>` зависит от байтов всех ресурсов и шаблона SW. SHA-256 проверяется браузером через Fetch integrity **включая HTML**. Пакеты до шести ресурсов ограничивают потребление памяти. На ресурс установлен таймаут 15 секунд; редиректы и ошибочные HTTP-ответы отклоняются. Полная установка заканчивается только после записи всех ресурсов; при ошибке удаляется неполный кеш кандидата. Старая активная версия остаётся доступной.

Для пяти маршрутов, включая query string и завершающий `/`, навигация возвращает оболочку из кеша. JS/CSS/изображения из списка сборки обслуживаются из кеша. При утрате HTML используется сеть с таймаутом четыре секунды либо понятная страница 503 с предложением повторить загрузку. Посторонние API и внешние запросы не добавляются в кеш.

Активный SW отвечает через MessageChannel на `GET_OFFLINE_STATUS`, проверяя наличие **каждого** необходимого ресурса. Только подтверждённый полный кеш даёт статус «Доступно без интернета». При неполном кеше `PREPARE_OFFLINE` восстанавливает отсутствующие файлы онлайн. Регистрация и проверка повторяются при запуске, `online`, возвращении видимости, смене контроллера и по кнопке. В профиле есть состояния подготовки и ошибки. Надпись «Офлайн» остаётся ненавязчивой и доступной для screen reader. Проверки и сетевые запросы SW не блокируют локальную инициализацию приложения.

Новый SW ждёт активации; при ручном обновлении сначала завершаются текущие записи настроек. Второе открытое окно блокирует ручную активацию с понятным сообщением. Затем происходит одна перезагрузка. При активации удаляются только старые кеши точного формата приложения. **IndexedDB, её версия, пользовательские записи и настройки не изменялись и не удаляются.** Очистка данных сайта и переустановка для обновления не требуются.

[Рекомендации Expo по PWA](https://docs.expo.dev/guides/progressive-web-apps/) также выделяют генерацию SW отдельно от экспорта.

Публикация hotfix не выполнялась. Изменение настроек Cloudflare и deployment требуют разрешения пользователя по AGENTS.md. После публикации на **том же origin** проверить `precache-manifest.json`, полный список HTTP-ресурсов и предложение обновления старой установленной PWA. Не менять домен: хранилище привязано к origin.

## Проверка на физическом iPhone

1. После согласованной публикации подключить интернет. Открыть **уже установленную** PWA с экрана «Домой», затем профиль. При предложении обновления закрыть другие окна MassTracker и нажать «Обновить». Для новой установки сначала открыть сайт в Safari и добавить на экран «Домой».
2. В профиле standalone-приложения дождаться **«Доступно без интернета»**. Статус в отдельной вкладке Safari не заменяет этот шаг. Если подготовка не завершена, оставить приложение открытым и нажать «Подготовить офлайн-режим» при доступной сети.
3. Выбрать тёмную тему. Полностью закрыть PWA через переключатель приложений. Отключить Wi-Fi и мобильные данные; одного авиарежима недостаточно, если Wi-Fi остался включён.
4. Открыть значок с экрана «Домой». Проверить быстрый запуск, надпись «Офлайн», пять вкладок, SVG-иконки и график. Офлайн выбрать светлую тему, закрыть и открыть PWA ещё раз; проверить сохранённую тему.
5. Восстановить сеть. После следующей согласованной сборки на том же домене проверить обновление, сохранение темы и других существующих данных. Ещё раз повторить холодный запуск без сети. Данные сайта не очищать.
6. При повторении исходного сбоя зафиксировать: точную версию iOS, origin, запуск из Safari или с экрана «Домой», последний статус готовности, сообщение при запуске. При наличии Mac подключить iPhone и проверить установленное приложение через Safari Web Inspector: scope, active/waiting SW, ключи `masstracker-app-*`, наличие `/` и всех URL из `precache-manifest.json`, ошибки Fetch/Cache Storage. Это позволит установить причину именно на устройстве.

## Ограничения

- Первый запуск требует сети, HTTPS и завершения precache. Без подготовленного кеша автономный запуск невозможен.
- Safari/WebKit управляет квотой и удалением данных сайта. Приложение запрашивает persistent storage в standalone при поддержке API, но не может гарантировать, что ОС никогда не очистит origin. При полном удалении кеша нужна повторная подготовка онлайн. Резервное копирование остаётся этапом 15.
- `navigator.onLine` сообщает состояние соединения, но не гарантирует доступность интернета. Решение о готовности принимается по фактическому кешу; сетевые операции имеют ограничение ожидания.
- Изолированные окружения Safari/standalone и разные домены могут хранить данные отдельно. Схема IndexedDB не изменялась; нативная SQLite остаётся отдельным хранилищем.
- Открытое второе окно удерживает старую версию до закрытия или явной безопасной активации.
- Автоматизированная проверка выполнена на Windows. Реальный iPhone с iOS 27.2.1 и отдельная Linux-сборка остаются непроверенными окружениями.
