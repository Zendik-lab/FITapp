# Локальная база данных

Этап 03 сохраняет JSON `nutrition_state` версии 1 в прежнем `app_settings`: режимы, цель/профицит, рекомендуемые и ручные калории, целевые БЖУ, дату и версию алгоритма. Схема IndexedDB/SQLite остаётся версии 2: новый ключ не меняет структуру, миграция не нужна. Документ читается до записи; повреждённые/неподдерживаемые данные не заменяются дефолтами. Используются прежняя атомарная `apply` и очередь обновления PWA. [Формат и отказы](STAGE-03.md#хранение).

`apply(changes, expected?)` может атомарно проверить ожидаемое значение одного ключа перед пакетом записей. При конфликте транзакция откатывается с `SettingsConflictError`. Репозиторий питания передаёт исходный снимок, поэтому пересчёт другого окна не заменяет сохранённые ручные настройки. Проверка и запись находятся в одной `readwrite`-транзакции IndexedDB или exclusive-транзакции SQLite; схема и существующие вызовы без условия сохранены.

`SettingsStorage` предоставляет асинхронное чтение по ключу, снимок настроек и атомарное применение списка изменений. Строковое значение создаёт или обновляет запись, `null` удаляет её. Запись считается успешной после фиксации транзакции. `list()` и `apply()` дают основу для будущего экспорта и восстановления настроек. Формат резервной копии и пользовательский интерфейс запланированы на этап 15.

## IndexedDB в PWA

- База `masstracker` хранится в данных origin. Миграция 1 создаёт `app_settings` с `keyPath: 'key'` и полями `key`, `value`, `updatedAt`. Она добавляет `ru-KZ`, `metric` и `KZT`. `theme_mode` появляется при первом сохранении темы.
- При открытии выполняются миграции после текущей версии внутри транзакции IndexedDB. При ошибке изменения схемы откатываются. Ошибка или блокировка другим окном возвращает управление экрану запуска, который доступен с настройками по умолчанию и повторной попыткой в профиле.
- Записи пакета ставятся в одну `readwrite`-транзакцию. Успех возвращается после события `complete`. Отмена, ошибка запроса и превышение квоты возвращают ошибку. При изменении версии другим окном соединение закрывается для разблокировки миграции.
- В установленной PWA запрашивается `navigator.storage.persist()`, если API доступен. Браузер может отклонить запрос или очистить данные. Примеры из `demo-data.ts` остаются в памяти.

## SQLite на iOS

Приложение открывает `masstracker.db` через Expo SQLite. Файл хранится в каталоге данных приложения на устройстве. Совместимый API использует существующий репозиторий и SQLite-транзакцию для пакета изменений.

## Схема версии 1

| Таблица             | Поле         | Тип и ограничения     |
| ------------------- | ------------ | --------------------- |
| `schema_migrations` | `version`    | `INTEGER PRIMARY KEY` |
| `schema_migrations` | `name`       | `TEXT NOT NULL`       |
| `schema_migrations` | `applied_at` | `TEXT NOT NULL`       |
| `app_settings`      | `key`        | `TEXT PRIMARY KEY`    |
| `app_settings`      | `value`      | `TEXT NOT NULL`       |
| `app_settings`      | `updated_at` | `TEXT NOT NULL`       |

Миграция 1 добавляет базовые настройки `locale=ru-KZ`, `units=metric`, `currency=KZT`. Репозиторий возвращает строку или `null` для отсутствующей записи. Запись использует UPSERT по ключу с обновлением метки времени. Удаление передаёт ключ параметром.

Этап 01 использует ключ `theme_mode` в существующей таблице `app_settings`. Поддерживаются `system`, `light` и `dark`. Отсутствующее или неизвестное значение переключает приложение на системную тему. Строка создаётся при сохранении настройки через профиль. Схема остаётся версии 1.

## Инициализация и миграции

- Клиент открывает одно соединение для приложения. Параллельные вызовы ожидают один результат. При ошибке подключения или миграции следующая попытка открывает соединение заново.
- Клиент включает `foreign_keys`, устанавливает `busy_timeout` и запрашивает `journal_mode=WAL`. Если SQLite возвращает другой режим журналирования, приложение продолжает работу в возвращённом режиме с записью в журнал.
- История хранится в `schema_migrations`. Версии миграций идут подряд от 1. История базы должна совпадать с началом списка известных миграций по номерам и именам.
- В одной транзакции создаётся журнал схемы, читается история, применяются ожидающие миграции в порядке версии и добавляются записи об их применении. При ошибке вся транзакция откатывается.
- Соединение не передаётся потребителям до завершения миграций. Поэтому сторонние запросы к тому же соединению не могут попасть в транзакцию приложения. Обычная транзакция сохраняет настройку `foreign_keys` того же соединения.
- Повторная инициализация пропускает зарегистрированные миграции. Ошибка не приводит к удалению или пересозданию файла базы.

## Изменение схемы

Для изменения добавьте миграцию со следующим номером и неизменяемым именем. Сохраняйте SQL опубликованных миграций. В `execAsync` передавайте только статический SQL из исходников, для пользовательских и других динамических значений используйте привязку параметров. Проверяйте создание чистой базы, обновление с предыдущей версии и повторный запуск после обновления.

## Версия 2 — профиль и анкетирование

SQL-миграция `002-user-state.ts` (`add_user_state_schema`) и вторая миграция IndexedDB добавляют `user_state_schema=1`. Существующие таблица / object store и настройки сохраняются. Версия SQLite / IndexedDB — 2, версия JSON-документа — 1; они независимы от версии Service Worker.

`createProfileRepository` работает через существующий `SettingsStorage`. Для одного локального пользователя отдельные таблицы не требуются: ключ `user_state` содержит один атомарный документ. Пользовательские значения передаются существующему параметризованному UPSERT. UI не содержит SQL.

| Поле JSON              | Содержимое                                                                                                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `version`              | `1`; неизвестная версия отклоняется без перезаписи                                                                                                                                |
| `profile`              | Проверенные поля анкеты или `null`; при чтении преобразуются в `UserProfile` с числовыми значениями и вложенными `personal`, `body`, `goals`, `activity`, `training`, `nutrition` |
| `onboarding.completed` | Подтверждённое завершение анкеты                                                                                                                                                  |
| `onboarding.step`      | Последний сохранённый шаг, индекс 0–7                                                                                                                                             |
| `onboarding.draft`     | Все поля `ProfileDraft`, включая незавершённые строковые значения; десятичная запятая сохраняется                                                                                 |

В JSON профиль хранится в форме нормализованного `ProfileDraft`; репозиторий повторно валидирует его и выдаёт типизированный `UserProfile`. Дата рождения — календарная строка `ДД.ММ.ГГГГ`, возраст вычисляется при отображении, без UTC-сдвига. Признак завершения и профиль записываются одним `apply`, без промежуточного частичного состояния. Повтор анкеты меняет только `onboarding`, сохраняя текущий профиль до нового подтверждения. Отдельное редактирование проходит общую валидацию и атомарно заменяет агрегат.

Все принятые записи регистрируются и выполняются последовательно в `settings-writes.ts`. Обновление PWA ожидает всю очередь; при ошибке записи обновление прекращается. Ошибка не подтверждает завершение или переход. Повреждённые данные остаются в хранилище; показывается экран ошибки с повторной попыткой. Черновик в анкете остаётся на экране и может быть сохранён повторно. При полном отказе IndexedDB сохраняется прежний ограниченный демонстрационный режим без возможности создать профиль.

## Даты и время

`applied_at` и `updated_at` хранятся как текст в UTC в формате ISO 8601 с миллисекундами и суффиксом `Z`. Для меток JavaScript используется `Date.toISOString()`, для начальных значений в SQLite — эквивалентный `strftime`. Перевод в часовой пояс устройства выполняется при отображении. Даты без времени, когда они появятся в профильных модулях, следует моделировать отдельно как календарные даты.
