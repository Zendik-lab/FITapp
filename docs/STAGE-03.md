# Этап 03 — Nutrition Calculation Engine

Дата: 26.11.2026. Код подготовлен в текущей ветке, без push и публикации. Статус `IN_PROGRESS` до ручной приёмки физического iPhone, установленной PWA и Expo Go. Этап 04 не начат.

## Реализовано

- Формула Миффлина — Сан Жеора для взрослых 18–120 лет, BMR и пять коэффициентов TDEE. Тренировки включены в активность и отдельно не прибавляются.
- Набор +200 / +350 / +500 ккал; стандартный режим по умолчанию. Совместимость с поддержанием и снижением: поправки 0 / −350 ккал. Фиксированный дефицит — решение реализации, адаптация по динамике веса не добавлена.
- Белки 1,8 г/кг, жиры 1 г/кг, углеводы из оставшейся энергии. Калории округляются до целых перед расчётом, граммы до десятых; проверка 4/9/4 с допуском 2 ккал. Проверяются исходные числа и итог после округления. Проценты неотрицательны и в сумме дают 100%.
- Независимые автоматический/ручной режимы калорий и БЖУ, предпросмотр, распределение, сохранение, восстановление рекомендаций и подтверждение отмены.
- Единые цели для «Сегодня», питания, профиля и калькулятора. Правки профиля пересчитывают рекомендации; ручные значения сохраняются. В ручном режиме отдельно показаны новые рекомендуемые калории и граммы БЖУ. Ошибка рекомендованных макросов не блокирует корректную ручную настройку.
- При отсутствии необходимых данных нет подстановок. Неуказанный пол или возраст менее 18 лет предлагают исправить профиль. Результат обозначен как ориентир без гарантии скорости изменения веса.
- Для личного профиля потребление еды равно нулю, демонстрационные приёмы пищи не показываются. Вода и тренировки прошлых этапов сохраняются с пометкой демонстрации; аварийный read-only режим недоступного хранилища сохранён.

## Архитектура

`src/features/nutrition/engine.ts` — чистые типизированные `calculateBMR`, `calculateTDEE`, `calculateCalorieTarget`, `calculateMacros`, `calculateMacroCalories`, `calculateMacroDistribution`, `validateNutritionTargets`. Модуль не зависит от React, сети и платформенного хранилища.

`model.ts` определяет настройки, рекомендации и снимок. `resolveNutrition` связывает движок с актуальным профилем. Подпись данных включает возраст, пол, вес, рост, активность, цель и настройки. Общий календарь инициирует проверку после смены дня / возвращения приложения. Количество тренировок не создаёт второй расход энергии.

`nutrition-provider.tsx` загружает документ до любых записей, публикует общий контекст, пересчитывает цели по изменению исходных данных. Ручное сохранение подтверждается после commit. Ошибка чтения блокирует только расчёты/сохранение питания, оставляя остальные вкладки и профиль доступными, и предлагает повтор без очистки. Ошибка автоматической записи допускает повтор; отказ ручного сохранения остаётся в форме вместе с вводом. `nutrition-context.ts` отделяет потребление от загрузки.

`daily-totals.ts`: `getDailyNutrition(targets, consumed)` — граница будущего дневника, сейчас без записей итог равен нулю. Сущности еды и операции дневника не реализованы.

Калькулятор использует существующие `FormScreen`, `FormField`, `ChoiceGroup`, `Card`, `Dialog`, тему и Safe Area; открывается внутри вкладки по образцу редактора профиля. Пять вкладок сохранены. Числовые поля остаются строками до сохранения: точка/запятая, без переформатирования каждого символа и смены ключей. Общий `FormField` на web становится редактируемым после commit регистрации ref: это завершает начальный эффект восстановления selection в React Native Web до первого ввода. Ввод не форматируется, фокус/курсор принудительно не устанавливаются, последующие обновления не меняют ref. Нативное поведение сохранено. Чистая форма принимает общие цели, сохранённые из другой вкладки; изменённый черновик при конфликте сохраняется на экране, запись блокируется до явной загрузки актуальных целей. Открытая форма блокирует применение PWA-обновления; отмена несохранённых правок требует подтверждения, перезагрузка защищена beforeunload.

## Хранение

Новый ключ `nutrition_state` в существующем `app_settings`, JSON версии 1:

- `preferences`: режим набора, режимы калорий/БЖУ, ручные калории и макросы;
- `goal`, `surplus`, `recommendedCalories`, `targets`;
- `calculatedAt` (ISO), `algorithmVersion: mifflin-1`, `profileSignature`.

Структура таблицы / object store не меняется: миграция схемы не нужна. SQLite и IndexedDB остаются версии 2. Отсутствующий ключ читается без записи дефолтов. Повреждённая/неизвестная версия не заменяется начальными данными. Перечисления принимают только настоящие строки. Запись проходит прежнюю атомарную транзакцию и очередь обновления PWA; профиль, тема и анкета не затрагиваются.

Общий `SettingsStorage.apply(changes, expected?)` дополнен необязательной проверкой ожидаемого значения в той же транзакции. Прежние потребители продолжают вызывать `apply(changes)`. IndexedDB сравнивает и пишет внутри `readwrite`, SQLite — внутри exclusive-транзакции с параметризованными запросами. Несовпадение даёт `SettingsConflictError`, без перезаписи документа. Репозиторий питания связывает запись с исходным снимком: даже параллельное повторное чтение не разрешает устаревшую запись. Автоматический пересчёт при конфликте загружает последние настройки, сохраняет ручную цель и повторяет расчёт по текущему профилю. Возвращение приложения на передний план также обновляет настройки из хранилища. Это защита локального документа при нескольких окнах, без backend или новой схемы.

Правка профиля и сохранение пересчитанного снимка — отдельные подтверждённые операции. Если вторая не удалась, актуальные цели вычисляются из профиля, отображается ошибка и повтор. После запуска пересчёт повторяется. Если автоматические калории перестали соответствовать ручным БЖУ, показывается предупреждение без самовольной замены граммов.

Safari управляет сроком хранения origin. Нельзя гарантировать сохранность после системной очистки, удаления данных сайта/приложения или смены origin. Резервное копирование остаётся этапом 15. В штатном сценарии проверяется восстановление после закрытия браузера/соединения, offline и reload.

## Ручная проверка iPhone

1. После разрешённой публикации `dist` на HTTPS проверить прежний origin и установленную PWA, согласованное применение версии и «Доступно без интернета».
2. В Safari ввести контрольные данные, открыть калькулятор из профиля и питания. Сверить расчёты, пять вкладок, портретный режим, верхнюю строку состояния, Home Indicator, обе темы и отсутствие горизонтальной прокрутки.
3. В ручные калории посимвольно ввести `3000,0`, исправить середину, удалить и повторно ввести цифры. При прокрутке и открытой клавиатуре проверить фокус, курсор и доступность нижних кнопок.
4. Ручные БЖУ `150 / 80 / 410` должны показать несоответствие при сохранении. Исправить углеводы на `420`, сохранить. «Сегодня» — 0 из 3000 ккал и нулевые употреблённые БЖУ.
5. Вес 72 → 73 кг: рекомендации 3241 ккал и БЖУ 131,4 / 73 / 514,6 г, ручная цель 3000 и граммы 150 / 80 / 420 сохранены. Закрыть и запустить PWA. Восстановить рекомендации и сохранить: автоматическая цель 3241 ккал.
6. В авиарежиме закрыть PWA из переключателя, запустить с домашнего экрана, открыть калькулятор, изменить и сохранить, снова перезапустить без сети. Проверить профиль, тему, цели, отсутствие фиктивной еды. Повторить после перезапуска устройства.
7. Пол «Не указывать» и возраст менее 18 лет → сообщение и переход к профилю, без вымышленных чисел.
8. Повторить ввод, сохранение, восстановление, правку профиля, Safe Area и клавиатуру в Expo Go.
9. Открыть калькулятор в питании, затем сохранить другую цель из профиля. Чистая первая форма принимает новую цель; при несохранённых правках предлагает загрузить актуальные значения и не разрешает перезапись. В двух Safari-окнах сохранить ручные 3000 в первом, изменить только вес во втором: ручная цель сохраняется.
