# Этап 02.1 — PWA Update & Offline Reliability

Дата: 26.11.2026. Реализация в `main`. Публикация не выполнялась; этап 03 не начат. Приёмка опубликованной версии и физического iPhone остаётся обязательной.

## Диагностика

Проверен опубликованный origin `https://fitapp-epj.pages.dev`, а не только исходники:

- `/sw.js` содержит сборку `0d9050edcee46277b988`. В `navigate()` есть безусловный возврат `shell` из кеша **перед** обращением к сети. Поэтому обычная перезагрузка установленного приложения продолжает запускать старый HTML и старый JavaScript.
- HTML и worker возвращались с `Cache-Control: no-cache, no-transform`. Для worker также наблюдались `CF-Cache-Status: HIT` и `Age`; сами по себе эти заголовки не доказывают, что CDN выдаёт неправильную версию. Заголовки HTTP не исправляют Cache First внутри SW.
- `/version.json` и `/precache-manifest.json` на опубликованном сайте возвращали HTML SPA fallback с HTTP 200 и `Content-Type: text/html`, а не сведения о версии.
- Manifest имеет стабильные `id`, `start_url`, `scope` `/` и `display: standalone`; его изменение или переустановка PWA не нужны.
- В исходной регистрации уже были `updateViaCache: none`, online/visibility и ручной `skipWaiting` с проверкой других окон. Однако ошибки проверки скрывались, самостоятельной проверки версии не было. Локальные блокировки редактора существовали, но требовалась общая защита всего времени заполнения формы.

Причина в поставляемом коде воспроизведена в настоящем Chromium: после контролируемого reload счётчик серверных запросов HTML не увеличивался. Новый регрессионный тест сначала упал на этом условии, затем прошёл после исправления. Состояние worker и открытых окон конкретного iPhone без подключения телефона не исследовалось; индивидуальное состояние устройства не выдаётся за установленный факт.

## Механизм обновления

1. `npm run build:web` выполняет существующий экспорт Expo и создаёт новый случайный 20-значный hex ID для каждого production-запуска, даже при неизменном коде. Версия приложения берётся из `package.json` (`0.1.0`). Метаданные согласованы в HTML, `version.json`, worker и precache-манифесте.
2. HTML запрашивается по сети с `no-store`, тайм-аутом 4 секунды и SHA-256 текущей сборки. HTML следующей сборки не смешивается с ресурсами работающей: до подтверждения обновления возвращается предыдущая согласованная оболочка. При потере сети используется её кеш.
3. JS, CSS, изображения и локальные шрифты кешируются в кеше конкретной сборки. Хешированные ресурсы неизменяемы. Стабильные URL HTML-ресурсов получают `?app-build=<id>`, чтобы выбирать ресурсы своего документа даже при смене контроллера другим окном. Потерянный ресурс текущей сборки восстанавливается только с проверкой integrity; HTML вместо JS/CSS не принимается.
4. При запуске, `visibilitychange`, `pageshow`, восстановлении сети, раз в час при видимом приложении и по кнопке выполняются проверки. Локальная регистрация обнаруживается и без сети: уже скачанное ожидающее обновление доступно после офлайн-перезапуска. Сетевые запросы worker и `version.json` обходят HTTP-кеш. Проверки не задерживают чтение IndexedDB и показ приложения.
5. Новый worker устанавливается только после полного precache, с проверкой SHA-256, запретом redirect, максимум шестью одновременными загрузками и тайм-аутом каждого ресурса. Повреждённый кандидат удаляет собственный неполный кеш, оставляя рабочую версию.
6. Автоматически выполняются обнаружение и загрузка. Применение — по «Обновить»; «Позже» скрывает уведомление до повторной проверки/открытия или другого кандидата. Профиль показывает версию, ID сборки, результат проверки и понятную ошибку с возможностью повторить действие.
7. Любой открытый `FormScreen` и диалог темы блокируют применение. Проверка защиты повторяется непосредственно перед активацией и reload. Все ранее принятые записи должны завершиться commit; сбой отменяет обновление и разрешает повторное сохранение. Worker проверяет остальные окна после ожидания проверки кеша.
8. После смены контроллера выполняется один явный reload. `controllerchange` сам по себе не перезагружает приложение. `sessionStorage` хранит последний целевой ID и предотвращает повторный reload той же сборки. Если браузер сразу активировал B при открытом HTML A, предлагается тот же безопасный переход на уже активный worker; готовность офлайн не подтверждается до совпадения версий документа и worker.
9. Список предшествующих кешей фиксируется **в начале установки**, до появления кеша следующей сборки, и хранится в заголовке кешированной оболочки. Удаление разрешено после запуска документа новой сборки, проверки его полного кеша и при отсутствии других окон приложения. Кеш одновременно устанавливаемой C не удаляется при применении B. При позднем появлении другого окна предшественники сохраняются; его хешированные ресурсы доступны из старого кеша.

Изменений схемы/миграций нет. IndexedDB, SQLite, localStorage и пользовательские настройки не очищаются. Единственная запись sessionStorage — служебная защита reload. Чужие кеши не удаляются.

## Заголовки Cloudflare Pages

| Ресурс                                               | Политика                                            |
| ---------------------------------------------------- | --------------------------------------------------- |
| HTML, manifest, обычная статика                      | `no-cache, no-transform`                            |
| `/sw.js`, `/version.json`, `/precache-manifest.json` | `no-store, no-cache, must-revalidate, no-transform` |
| `/_expo/static/*` с хешами в именах                  | `public, max-age=31536000, immutable, no-transform` |

`public/_headers` копируется в `dist`. Перед переопределением используется `! Cache-Control`, чтобы правила Pages не объединяли конфликтующие директивы. Локальный статический сервер применяет тот же файл; браузерные тесты проверяют реальные ответы HTTP. После разрешённой публикации требуется повторить проверку на production: локальная проверка не подтверждает применение правил удалённым CDN.

Поведение сверено с первичными источниками: [ServiceWorkerRegistration.update](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/update) и [Cloudflare Pages: headers](https://developers.cloudflare.com/pages/configuration/headers/).

## Проверка на iPhone

Не удалять PWA, не очищать данные Safari и не выполнять сброс хранилищ.

1. После отдельно разрешённой публикации открыть существующую PWA на **том же** origin `https://fitapp-epj.pages.dev` при доступной сети. Для первой миграции со старого кода может потребоваться закрыть остальные окна MassTracker и снова открыть PWA: новые проверки появятся только после первого применения новой сборки.
2. В «Профиль» записать версию и ID сборки A. Дождаться «Доступно без интернета». Изменить имя и целевой вес, сохранить, полностью закрыть и открыть PWA. Проверить значения.
3. Включить авиарежим, отключив также Wi-Fi. Закрыть PWA через переключатель приложений и открыть с домашнего экрана. Проверить пять вкладок, профиль и цели. Изменить профиль и целевой вес офлайн; сохранить, закрыть и открыть снова.
4. После разрешённой публикации сборки B на том же origin восстановить сеть и вернуть PWA из фона. Уведомление должно появиться без переустановки. Проверить также кнопку «Проверить обновления».
5. Нажать «Позже»: текущая версия должна работать. Начать редактирование имени; при предложенном обновлении кнопка должна быть заблокирована, текст поля сохранён. Сохранить форму и выйти из редактора.
6. Открыть то же приложение в другом окне Safari. Попытка применения должна попросить закрыть другие окна. Закрыть их, нажать «Обновить» один раз. Убедиться, что ID сменился на B, данные/тема сохранились, повторных reload нет.
7. Снова включить авиарежим, полностью закрыть и открыть PWA. Проверить вкладки, профиль и цели уже на B. Дополнительно скачать очередное обновление онлайн, перезапустить PWA офлайн и применить готовое обновление без сети.
8. На тестовом origin прервать загрузку обновления / вернуть 503 для worker или версии. Прежнее приложение должно оставаться рабочим; повторить после восстановления сервера. Зафиксировать модель iPhone, версию iOS, IDs A/B и результаты.

Playwright WebKit на Windows не подменяет Safari, установленный standalone-контекст, эвикцию хранилищ и приостановку приложения настоящей iOS. Системные снимки экрана запуска и возврат из глубокой приостановки проверяются вручную. Safari может очистить локальное хранилище по своей политике; резервное копирование остаётся в этапе 15.
